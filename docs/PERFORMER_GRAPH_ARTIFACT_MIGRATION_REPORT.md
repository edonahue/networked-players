# Performer graph artifact migration report (ADR 0068 PR 3, 2026-09-01)

Real, measured before/after comparison for the two graph-dependent public
artifacts regenerated under ADR 0068's performer gate:
`pathfinding/graph.v3.json` and `challenge.v3.json`. Both are published as
new, dual-live files alongside their unedited `v2` counterparts — **no
production cutover happens as part of this PR.** `graph.v2.json` and
`challenge.v2.json` remain byte-identical to before, still fetched by every
real live page/consumer; `graph.v3.json`/`challenge.v3.json` exist,
validate cleanly, and are registered in `PUBLIC_ARTIFACT_GROUPS`, but
nothing live points at them yet. That cutover is explicitly PR 4's job
(pathfinding graph, Connect/Explore) and PR 5's job (challenge, homepage,
albums, contributors, copy).

Built from the real one-hop working set
(`local/processed/discogs-onehop-v4/snapshot=20260601`) against the real,
currently-published canonical catalog (`catalog-v1-20260601-7fbbb46b28e6`,
179 albums), 2026-09-01.

### Every catalog album's largest-component membership, before and after

Computed via a real union-find over each graph's actual CSR adjacency
(`node_ids`/`offsets`/`neighbors`), not estimated. Both `graph.v2.json` and
`graph.v3.json` are themselves a single connected component — every real
node reaches every other real node — so "largest component" and "the whole
graph" are the same set in both cases.

**All 179 of 179 real catalog albums are in the largest component both
before and after. Zero albums newly isolated. Zero albums newly joined
(none were isolated to begin with).** This is the strongest possible
result: the performer gate roughly halves the graph's size (fewer
non-performing "everyone connects to the prolific producer" edges) without
disconnecting a single real catalog album from the rest.

This closes the loop on the approved plan's own preliminary hypothesis
("~24K/76K undirected edges, ~170/179 albums retained, ~6 isolated
anchors") — that hypothesis was written against the wrong *scale* (PR 2's
shadow report already discarded it for describing the full one-hop corpus
instead of this bounded graph), but its rough *shape* was closer to this
bounded-graph comparison: v3's real undirected edge count is 38,323
(76,646 directed ÷ 2), the same order of magnitude as the "~76K" figure —
plausibly what that hypothesis was actually gesturing at, even though it
undercounted by roughly 2x and (correctly, as it turned out) overestimated
the isolated-anchor risk at ~6 versus the real 0.

**Paths get longer, which is the expected and honest consequence of the
gate.** Removing non-performing edges removes shortcuts, so connections that
previously resolved in 2 hops now need 3. The distribution shifts right
(2-hop 185 → 137, 3-hop 104 → 150) without the artifact losing coverage:
still 300 real paths across all 179 albums, and 16.7% fewer distinct artists
referenced, consistent with a graph that no longer routes through
producers/engineers/mastering engineers.

### A build-performance finding that changed the result materially

The first four attempts to build this artifact used the pre-existing DuckDB
search path and **did not complete**, each running 1–2 hours before being
killed, at progressively tighter `--max-frontier-expansion` values
(300 → 150 → 50 → 25). The one that did finish (frontier 25, `--max-paths
100`) produced a badly degraded artifact, and the degradation was a
measurement artifact rather than a fact about the music:

| | capped attempt (frontier 25) | this artifact (uncapped, in-memory) |
| --- | ---: | ---: |
| Searches attempted | 13,179 | **302** |
| Searches refused by the cap | 13,079 (99.2%) | **0** |
| Paths found | 100 | **300** |
| Albums appearing in ≥1 path | 68 / 179 | **172 / 179** |

Root cause: `max_frontier_expansion` is a **per-node out-degree threshold**,
not a total-work budget. Catalog albums are billed to systematically
high-degree artists (Elton John 895, Miles Davis 753, Herbie Hancock 744 in
the gated graph), so any cap low enough to make the DuckDB path finish also
refuses to expand from the very artists every search must start at. There is
no good value; the mechanism is wrong for this workload.

The fix (`InMemoryEdgeIndex`, added in this PR) runs the identical BFS over
an in-memory copy of `credit_edges` instead of issuing ~8 SQL round-trips
per pair. The relation is small — 1,677,134 directed edges over 253,448
artists, ~13MB — fetching in 1.9s and indexing in 5.8s. Measured over all
14,878 real candidate pairs with no cap: 636s total (42.7ms/pair), 14,343
paths found (96.4%). That made `--max-frontier-expansion 0` (no cap at all)
affordable, which is what this artifact was actually built with.

`test_in_memory_find_path_matches_the_duckdb_implementation` and its
companion diamond-shaped ordering test assert the two implementations return
*identical* paths, not merely both-valid ones — this is a substrate swap,
not a different algorithm.

**One honest caveat on the 172/179 figure:** it is a lower bound set by
`--max-paths 300` stopping the search after only 302 candidate pairs, not a
statement about connectivity. The 7 albums absent from this artifact's paths
are *not* disconnected — the union-find analysis above proves all 179 sit in
`graph.v3.json`'s single connected component. They simply did not come up in
the first 302 pairs the lazy iterator consumed.

*Resolved 2026-09-02 (graph-expansion Phase 0, slice 0-A):* the cause was the
candidate-pair order itself — `for i: for j > i` over id-sorted albums meant
every one of the 300 paths started from the same two albums. `_candidate_album_pairs`
now hands each album its own turn per round (per-album round-robin, deduplicated
per artist pair) and `--max-paths` defaults to twice the album count, so the
regenerated `challenge.v3.json` reaches all 179 albums with 358 paths, every album
on at least two of them. The contributor index, hop distances, and evidence registry
were regenerated from it in the documented order; the before/after diff is recorded
in `local/benchmarks/` (private per ADR 0018).
